# Database

## Engine

SQLite by default (`DATABASE_URL=sqlite:///./annadata.db`), zero-config. The SQLAlchemy models use no SQLite-specific types or features, so pointing `DATABASE_URL` at a `postgresql+psycopg2://` DSN and running `alembic upgrade head` against it is the entire migration path — no model or query rewrites needed.

## Migrations

Managed with Alembic (`backend/alembic/`). The initial migration (`ba7258609935_initial_schema.py`) was autogenerated from the SQLAlchemy models and creates all 27 tables. Run `alembic upgrade head` from `backend/` to apply.

## Entity overview

| Table | Purpose |
|---|---|
| `users` | One row per login-capable account; `role` discriminates the six roles |
| `farmer_profiles`, `fpo_agent_profiles`, `buyer_profiles`, `assayer_profiles`, `transporter_profiles` | Role-specific profile data, each 1:1 with a `users` row |
| `fpo_organizations` | The FPO/collection-centre entity a farmer or FPO agent belongs to |
| `commodities` | Crop reference data (onion for the pilot), including `storage_guidelines` JSON used by the IoT threshold logic |
| `storage_facilities` | Third-party storage facilities AnnData coordinates with (not owned by AnnData) |
| `lots` | An aggregated batch of produce; `status` drives the workflow state machine |
| `lot_contributors` | Per-farmer quantity share within a lot (many-to-many, `lots` ↔ `farmer_profiles`) |
| `lot_media` | Uploaded photos/documents attached to a lot, tagged by workflow stage |
| `preliminary_screenings` | The local deterministic "AI" screen result (1:1 with `lots`) |
| `quality_assessments` | The assayer's authoritative physical assessment (1:1 with `lots`), immutable once `is_finalized` |
| `offers` | Buyer offers against a lot, with the full deduction breakdown |
| `purchase_orders` | The contract created when an offer is accepted; freezes price/deduction/tolerance terms |
| `shipments` | Transporter assignment and pickup/delivery tracking |
| `storage_bookings` | A lot's reservation at a storage facility |
| `storage_events` | Simulated IoT sensor readings, optionally linked to a booking |
| `payments` | Mock payment record per purchase order |
| `settlements` / `settlement_items` | The per-lot settlement total and its itemized per-farmer breakdown |
| `disputes` / `dispute_evidence` | Dispute records and their attached evidence |
| `audit_logs` | Append-only log of every important mutation |
| `notifications` | In-app notifications per user |
| `consent_records` | Per-user consent records (schema present; full capture UI not built in this MVP) |

## Indexes

Indexes exist on every foreign key used in a hot-path filter (`Lot.status`, `Lot.fpo_id` via query filters, `AuditLog.entity_type`/`entity_id`/`action`/`created_at`, `Notification.user_id`/`created_at`, `StorageEvent.recorded_at`, and the unique lookup columns `User.email`, `Lot.lot_code`, `PurchaseOrder.po_number`).

## Money representation

Monetary and weight fields use `Float` rather than a fixed-point `Decimal`/`Numeric` type. This is a deliberate scope trade-off for the demo: it keeps arithmetic simple across the API, JSON serialization and the frontend, at the cost of theoretical floating-point rounding drift on money. `services/settlement.py` compensates for this in the one place it matters (settlement line items) by adjusting the final line to absorb rounding drift so itemized amounts always sum exactly to the distributable total. A production system handling real payments should migrate money fields to `Numeric`/`Decimal`.

## Seed data

`backend/scripts/seed.py` creates the full pilot reference dataset (one FPO, three synthetic farmers, three buyers, one assayer, one transporter, one storage facility, one admin) and carries one 2,000kg onion lot through the entire workflow to a resolved dispute, so every dashboard has meaningful data immediately. `backend/scripts/reset_demo.py` drops and recreates the schema before reseeding. **Every seeded person, organization and transaction is explicitly synthetic** — see the README's demo-data disclaimer.
